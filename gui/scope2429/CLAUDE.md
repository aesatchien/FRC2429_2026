# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The folder holds one Python tool, **Scope2429**, written for the 2026 season (REBUILT) and kept in the 2429 robot repo (`FRC2429_2026`) as `gui/scope2429/`, so it uses only libraries that repo's GUI already needs (numpy, opencv, pyntcore) plus Tkinter; `yt-dlp` and `imageio-ffmpeg` are optional and imported lazily. Season-specific things (field, dashboard replica, topic names, scoring model) are 2026's; the next season starts from a copy. The robot `.wpilog` match logs it was developed on (`WPILIB_<date>_<time>_<event>_<P|Q|E><n>.wpilog`, event `CAEL`, 2026) are not kept in the repo (`.gitignore`). Scope2429 (was LogScope, earlier `match_video/`) LogScope shows the team's dashboard layout (field, indicators, telemetry panels) from a `.wpilog` or from a live NetworkTables 4 connection (roboRIO `10.24.29.2`, a simulator, any address). The top-right slot is the YouTube match video, or scrolling trend plots when there is no video. It can render an MP4. A log without a match (shop practice) or without a video is fine: FMS-only info shows defaults. It is part of the `FRC2429_2026` git repo (the root `.gitignore` already ignores `*.wpilog` and `*.hoot`), and the repo-wide CI lint covers it, but it has no test suite or build step of its own. See [README.md](README.md) for the user-facing workflow.

## Commands

Run from this folder:

- Install: `pip install -r requirements.txt` (numpy, opencv-python, pyntcore, yt-dlp, imageio-ffmpeg; the last two are still imported lazily, but are listed as requirements so a fresh install can open a video)
- Launch GUI: `python scope2429.py` (no launch scripts; use the `robo2026` environment, since it needs the 2026 `pyntcore`)
- Layout: the entry points (`scope2429.py`, `report.py`, `report_window.py`, `report_image.py`, `season_report.py`, `sysid.py`) and the data folders (`assets/`, `fields/`, `report_templates/`) are in this folder; every library module (`core`, `dash`, `dash_left`, `telemetry`, `trends`, `live`, `hoot`, `webcast`, `balls`, `scorebug`, `gui_layout`) is in `helpers/`. The modules import each other by plain name, so the entry points put `helpers/` on `sys.path` (see the top of `scope2429.py`, `season_report.py`, `sysid.py`); a new entry point must do the same. Modules in `helpers/` reach the data folders with `Path(__file__).resolve().parent.parent`.
- `core.py` (in `helpers/`) can be imported from scripts without the GUI, with `helpers/` on the path: `load_match_log`, `auto_sync`, `render(RenderJob(...))`.

Runtime state lives outside the repo in `~/.scope2429/` (renamed from `~/.logscope/` / `~/.frc_match_video/` on first start; `load_settings` rewrites stored cache paths) (`settings.json`, `cache/` for downloaded videos, `bin/` for the copied ffmpeg, `fields/`). Rendered videos default to `<logs folder>/videos/`. Settings hold per-log offset/URL/title and a `rendered` flag, which the batch run uses to skip logs.

## Architecture

`core.py` has no UI dependencies, and `scope2429.py` is a Tkinter front end over it. `live.py` is the NT4 source, `trends.py` the no-video slot.

**Sources and defaults (read this before touching time handling).** `MatchLog.t_ref` is time zero of every plot: `auto_start`, else the first enable, else the first record. `has_match` (= `auto_start is not None`) gates everything FMS-only: the match clock (`Telemetry.match_time` returns None -> `--` tile), points/accuracy (`--`), auto-sync, TBA, the video render. `match_len` falls back to the log duration. Never use `ml.auto_start` as a time origin; use `ml.t_ref`. `PhaseTracker` turns control words into the phase times for both logs and the live session. `RenderJob.video` may be None.

**Live path.** `LiveSession.poll()` (called from the Tk thread, no worker thread) drains an ntcore listener queue into a `Telemetry(None, ...)`, whose signals are `LiveSig` (growing, capped). Log names are `NT:` + topic name, so the same keys work. `DashRenderer(..., tel=live_tel)` switches to live mode: the static plot bases become scrolling plots drawn per frame (x = seconds before now, `_live_plots` / `_live_line`), and `update_live` refreshes the things a log computes once (Mechanism2d tree, navX yaw offset, `ShotModel`). `GuiPanel` re-makes its static labels when a topic first appears. Time on the live clock is `ntcore._now()` based; `DS:joystick*` is not on NT, so the controller panels are blank live.

**core.py pipeline** (the pieces only make sense together):
1. `read_wpilog` is a hand-written, pure-Python binary parser (no robotpy). `load_match_log` filters by entry name and decodes `struct:Pose2d` payloads (3 little-endian doubles). It also derives auto/teleop start/end from the FMS control word (`DS:controlWord`, falling back to the NT copy), and reads match type/number/station from `NT:/DriverStation/*`. Poses outside the field bounds become NaN (QuestNav publishes -10,-10 before tracking). Match type/number fall back to the filename.
2. `tba_match_key` / `tba_find_video` map Qn → `qm n`, En → `sf n m1` (`f1m(n-13)` after 13) and look up the YouTube URL. They use the TBA API if a key is given, otherwise they scrape the TBA match page. Practice matches have no TBA entry.
3. `download_youtube` (yt-dlp, cached by video id, max 720p).
4. `auto_sync` builds an audio onset envelope (spectral flux, 400–3500 Hz) and slides the log's phase-event times (auto start/end, teleop start/end) over it. It returns the video time of auto start, plus a z-score confidence. The GUI and batch treat `conf > 6 and ratio > 1.15` as "good".
5. `FieldPanel` draws the field. Field images are AdvantageScope `Field2d_*` folders (`config.json` + image). They are found in AdvantageScope's asset dirs, then the bundled `fields/`, then the generated `synthetic_field()`. Poses are blue-origin WPILib metres. `FieldImage.native_px` maps them to image pixels, depending on `coordinateSystem` (`center-rotated` = blue origin top-right). `FieldPanel` rotates the image 180° (never mirrors) so red is on the left to match the broadcast. All coordinate maths must go through `native_px` / `to_px` so that rotation stays consistent.
6. `render` pipes raw BGR frames to an ffmpeg subprocess via stdin. In the default dashboard layout (`RenderStyle.dashboard`, forced when there is no video) the frame is the full 1920x1080 canvas from `dash.DashRenderer`, with the top-right 960x540 slot left black (or, with no video, filled by `trends.TrendPanel`). ffmpeg `overlay`s the scaled match video into that slot. The classic layout (`dashboard=False`) draws only the field panel and `hstack`s it with the video. Output is H.264 + AAC, `yuv420p`, faststart. `preview` builds a single frame the same way, and `get_dash` caches the (3 s to build) `DashRenderer` between GUI previews.
7. `telemetry.py` + `dash.py` (dashboard layout). `Telemetry` decodes all the signals the panels use into `Sig` time series (`at(t)` is sample-and-hold, in log time). That includes the DS joysticks, swerve `SwerveModuleVelocity[]` struct arrays, and the whole `Mech Side View` Mechanism2d tree. `ShotModel` counts balls fired from flywheel-rpm dips during indexer bursts. `VideoShotModel` (fed by `balls.measure`, one pass over the broadcast video, cached on disk keyed by offset and layout, only computed by a real `render`; previews use only a cache that matches the current offset) is the only source of points, and it uses ONLY the alliance fuel counter read by `scorebug.py` (11 digit templates embedded in the file, made by `make_templates` from frames labelled by eye). Nothing is counted from the picture any more: the yellow-fuel blob counting depended on camera angles that change between events and was removed (2026dal Q49). Which corner is which alliance follows the broadcast layout (`scorebug.red_left` / `detect_red_left`: red left at SoCal Showdown, blue left at Daly), so never index the corners by colour. The model credits 2429 with the counter ticks in a window after each burst of `ShotModel.bursts` (dips from inside the own alliance zone only, G407), capped at the shots fired; partners shooting in the same window are counted too, so it is an upper bound. Without a readable counter the score is 0. `DashRenderer.render(t)` draws the bottom telemetry panels and delegates the top-left quadrant to `dash_left.GuiPanel`. That class replicates 2429's PyQt dashboard window from `gui_layout.py`, a table generated from the robot repo's `gui/layout_2026.ui` (topics and styles come from the GUI's `config.py` / `ui_updater.py`). A widget whose topic has no samples in the log is deliberately left blank. The static parts are cached in `left_base` / `low_base` and only the dynamic parts are redrawn per frame. The pose mapping reuses `FieldPanel.to_px`, so the red-left rotation stays consistent.

**report.py** (no UI) builds a `Report` of `Section`s (items with a severity and a time after `t_ref`, plus a table) from a `Telemetry`: health, swerve, odometry, cycles. Each section only reports what its entries show and says what is not logged; `report_window.py` shows it and calls `App.seek`. New `Telemetry` keys it needs are in `SCALARS`.

**hoot.py** (no UI): `find_owlets` / `pick_owlet` choose the owlet build whose compliancy number matches the hoot (AdvantageScope's `owlet` folder, `~/.scope2429/bin`, PATH), `convert_hoot` runs `owlet in out -f wpilog` (cached; a hoot that was not closed cleanly still converts, with a warning), `find_hoots_for_log` matches by event+match token in the file or folder name, and `HootLog.load` reads the converted wpilog (`Phoenix6/can_s0/TalonFX-<id>/<Signal>`) and shifts it to the robot clock by cross-correlating the RobotEnable signal with the robot's control-word enable intervals. `DEVICE_NAMES` / `MODULE_OF` hard-code the 2026 CAN ids. `report._hoot_section` adds the CTRE section when a `HootLog` is passed to `build_report`. `RenderJob.hoot` -> `DashRenderer(hoot=...)` draws the per-module drive current, fault ring / banner (`_hoot_module_tag`, `_hoot_banner`) and the PDH amps trace (`_hoot_drive_sum`); the GUI loads the hoot in a background thread (`_load_hoot_bg`) when a log is selected. `report._correlate` adds a first section of events from different sources that line up in time (items flagged `event=True`). `RenderJob.hoot` -> `DashRenderer(hoot=...)` draws the per-module drive current, fault ring / banner (`_hoot_module_tag`, `_hoot_banner`) and the PDH amps trace (`_hoot_drive_sum`); the GUI loads the hoot in a background thread (`_load_hoot_bg`) when a log is selected. `report._correlate` adds a first section of events from different sources that line up in time (items flagged `event=True`).

**sysid.py** (no UI): fits `volts = kS*sign(v) + kV*v + kA*a` to a hoot's drive-motor `MotorVoltage` and `Velocity` (rps, wheel side). The hoot logs Velocity at 100 Hz but MotorVoltage only at 4 Hz, so each MotorVoltage sample is a row (velocity interpolated, acceleration a centred difference); kS/kV come from the steady rows, Huber-weighted, and a kA with a wide standard error is flagged. `report._ff_section` adds the per-match table; `python sysid.py <logs folder> [out.json]` pools every match that has a hoot and prints the between-match spread (the honest uncertainty). `SYSID_SHOP_GUIDE.md` is the procedure for the confirming quasistatic / dynamic shop test.

**webcast.py** (no UI): cuts matches out of whole-day event streams. `locate` maps the log's `systemTime` wall clock to a position in the day video (`release_timestamp` = stream start); that is wrong by a few minutes, equally for every match of a day, so `calibrate` searches a few matches +-`WINDOW_S` and takes the majority delta (`cal` dict, persisted in settings as `day_cal`), after which `clip_match` uses +-`NARROW_S`. `download_segment_hls` fetches only the needed 5 s HLS files (video itag 311 + audio 234, ~15x real time, yt-dlp's own `download_ranges` is real time and needs ffmpeg on PATH) and remuxes them with ffmpeg. `core.auto_sync` returns the top audio candidates (`det['peaks']`); `check_start` confirms one by the fuel counters (0 at start) or by the match clock (`visual_start`: the ones digit stands still at 0:20, then changes 1 s after auto start), then the offset is moved to the picture because the stream's audio runs ~2 s late. NOTE: that description predates `clock_starts`, which is now the primary locator: it scans the clip's key frames (ffmpeg `-skip_frame nokey`) for the clock standing at 0:20 (minutes digit must be 0, otherwise 2:20 at teleop start matches), refines with `visual_start`, and for qualifications requires `team_visible` (template of the white text '2429' in the score bar) to reject the neighbouring match: consecutive matches are equally spaced, so a calibration vote cannot tell Q13 from Q14. `CLIP_VERSION` is stamped on renders so older clips are redone. YouTube needs a JS runtime (Deno) for the audio formats: `core.js_runtime_opts()`. `RenderJob.video` is the cached clip and `offset` the start inside it.

**scope2429.py**: `App(tk.Tk)`. Long work runs through `_run(fn, done, label)`, which starts a worker thread and posts `("progress"|"done"|"error")` tuples to a `queue.Queue`. `_poll` drains that queue on the Tk thread, so never touch widgets from a worker. Only one task can run at a time (`self.busy`). `_batch` runs the whole TBA → download → sync → render chain in one worker for every Q/E log and reports low-confidence syncs.

## Conventions and gotchas

- Default NetworkTables names are `DEFAULT_DRIVE = NT:/SmartDashboard/Swerve/drive_pose` and `DEFAULT_QUEST = NT:/QuestNav/quest_pose`. These are user-configurable in the GUI.
- The default TBA event key (`2026cass`) and title format (`2429 · SoCal Showdown …`) are hardcoded in `scope2429.py`.
- Robot console: comp_system_core saves everything the program prints to `console_<boot UTC>.log` in the wpilog folder (`comp_system_core/helpers/console_log.py`). Lines are `<robot time s> <UTC> <O|E> <text>`; the robot time is the wpilog clock, so `t - ml.t_ref` is the plot time with no conversion. `helpers/console_file.py` parses it and picks the file from the same boot as a log by the UTC time at robot time zero (the folder can hold several boots, and the robot clock restarts at every boot). `report._console` adds the section; `console_file.severity` decides what counts as a warning or error (keep it off the `***` banners the robot prints on purpose). WPILib's own `console` / `messages` wpilog entries were empty in every SoCal Showdown log, which is why this exists.
- Which side red is on is read from the video: `core.detect_red_left` compares the left and right score boxes of the broadcast score bar (fixed boxes in the 1280x720 frame, margin 100, needs 2 agreeing frames, else `None` = keep the checkbox). `App._auto_red_left` runs it when a video loads and `_batch` runs it per video. Checked on 13 cached match videos (SoCal Showdown red left, Daly Division blue left) against the red/blue field pixels; if a broadcast moves the score bar, change `SCORE_BOX_LEFT` / `SCORE_BOX_RIGHT`.
- Text drawn with `cv2.putText` must be ASCII: the Hershey fonts draw every other character as `?` (one per UTF-8 byte, so `·` and `°` show as `??`). `dash.put` / `dash.put_mid` pass text through `dash.ascii_text`, which maps the symbols we use (`·` to `|`, `°` to ` deg`, dashes, `…`, `±`, arrows). Use those helpers, not bare `cv2.putText`, for anything that can contain such characters (titles are typed by the user).
- Read JSON with `utf-8-sig` (`_read_json`), because Windows defaults to cp1252.
- Subprocesses use `creationflags=NO_WINDOW` to hide console windows on Windows.
- YouTube downloads need a JS runtime (Deno) and an up-to-date yt-dlp; `download_youtube`'s error text says so.
- The PDH POWER panel has three plots (volts, amps and, since 2026-10-25, CAN bus utilization %: `pc` in `_make_lower_base`, keys `can_s0/1/2_util` from `NT:/SmartDashboard/CAN/` written by comp_system_core `helpers/can_monitor.py`; `telemetry.can_util_scale` decides whether the logged unit is a fraction) and the strips below them (`STRIP_Y`) - change one of those heights and move the other. It shows volts and amps, brownouts (roboRIO flag, hoot BridgeBrownout, battery under `BROWN_V`) and three strips: camera / coprocessor (NT link drops from the log's `NTConnection` entry, frame-counter stalls and restarts), Quest connected, Wi-Fi (own link drops live, other NT clients' drops, gaps in the PDH voltage stream). Live it shows the last `PDH_WIN` = 180 s; a live client only sees its own link, so there the coprocessor shows as frame-counter stalls. `read_wpilog` clamps negative 64-bit times to 0, and `load_match_log` falls back to `DS:enabled/autonomous/test` when a log has no control word.
- The BUTTON BOX panel (`dash.py`: `_draw_bbox`, `_bbox_button`, `_bbox_toggle`) copies the physical operator box: `BBOX_XY` has the button centres (same grid as the box), `BBOX_RED` which are red, `BBOX_LABELS` the tape labels, buttons 0-9 are DS buttons on port 2 (0 based, as in the robot's `bbox_1.button(i)`), and 10 / 11 are the ends of the shooting-power toggle (10 = -50 on the left, 11 = +50 on the right, middle = none; the robot's bindings return the offset to 0 on release).
- Dashboard canvas (1920x1080, `dash.py`): top-left the GUI replica with the motor-rpm strip under it (`MOTOR_Y`), top-right the video / trend plots, bottom-left the Quest-vs-shot-accuracy plot (`CORR2_H` = 170) over the PDH POWER panel (y 170..540), bottom-right six 320x270 panels (mechanism, swerve, motor temperature / scoring, driver controller, button box). The right-hand panels are drawn into numpy views of the canvas with local coordinates (`_draw_mech`, `_draw_swerve`, `_draw_temps`, `_draw_scoring`, `_draw_driver`, `_draw_bbox`); the driver pad is drawn at 640x265 and shrunk.
